1. Goal and research question

Question. At about 4 bits per weight, how much accuracy do MXFP4 and NVFP4 lose compared with FP16 and INT4 on a small LLM, and does the 4-bit storage turn into speed on 32-bit general-purpose hardware without native FP4 support, compared with hardware that has it (NVIDIA Blackwell)?

Why this answers the professor's comment. He asked us to consider running these formats on specialized hardware versus 32-bit general-purpose hardware. E2 and E3 below measure and model exactly that, using our own Cortex-M4F board, which no other group has.

Claims from the literature we test (page numbers are in paper/references_verified.md):

  • MXFP4 loses noticeably more accuracy than NVFP4, about 10% relative in W4A4 (Egiazarian et al., ICLR 2026), and FP4 is "not an automatic upgrade over INT4". Tested by E1.
  • How the MXFP4 power-of-two scale is chosen matters: the OCP rule rounds down and clamps; NVIDIA rounds up to avoid saturation but wastes range. Tested by E4 at equal storage.
  • FP4 speedups need hardware support: 4-6× math over BF16 on Blackwell, but 4-bit can be slower than FP16 on hardware without native support (De-Quantization Penalties, IEEE CAL 2026). Tested by E2 and E3.

5. Experiments in detail

E1. Accuracy vs bits per element Ziad (preliminary results in the draft)

Setup. Weight-only, simulated ("fake") quantization: quantize each weight, convert straight back to float, run the model normally. This measures accuracy, not speed (speed is E2/E3). Quantize every linear layer's weight; keep embeddings, the output head, norms and biases in FP16, and say so in the paper.

FormatBlockScaleBits / weightRule
FP16 (baseline)n/an/a16none
INT4, group 128128FP16, symmetric4.125s = max|w| / 7, round, clamp to [−8, 7]
INT4, group 3232FP16, symmetric4.5same
MXFP4 (OCP)32E8M0 (power of two)4.25X = 2^(floor(log2 max|w|) − 2), round to E2M1, clamp at ±6
NVFP416E4M3 + FP32 per tensor4.5block scale = max|w| / 6, stored in E4M3; tensor scale keeps block scales in E4M3 range

Important detail. Group along the reduction (input) dimension. Hugging Face GPT-2 uses Conv1D layers whose weight is stored as (in, out), the transpose of nn.Linear (out, in) used by Qwen. Block along the input axis in both.

Correctness tests before any model run (put them in e1_accuracy/test_quant.py):

  • E2M1 grid is exactly ±{0, 0.5, 1, 1.5, 2, 3, 4, 6}.
  • HW3 Q3: A = [24, −12, 6, 2, 0…] gives X = 4 and elements [6, −3, 1.5, 0.5]; B gives X = 0.5 and [0.5, 2, −1, 4]; dot product −5.
  • Four Over Six, Table 2 (p. 5): NVFP4 of [10, 20, 30, 40] dequantizes to [9.75, 19.5, 26, 39] with MSE 4.33.

Perplexity. WikiText-2 raw test set, non-overlapping windows of 1024 tokens (GPT-2) or 2048 (Qwen), mean negative log-likelihood over all tokens, perplexity = e^NLL. Same windows for every format.

Also record for every format: weight MSE and signal-to-quantization-noise ratio (SQNR, in dB) over all quantized weights; fraction of weights clamped; bits per weight; run time.

Runs. 5 formats × 2 models = 10 runs. GPT-2 runs take minutes; Qwen3-1.7B runs may take 10-30 minutes each on MPS, so run them overnight with a script that writes one JSON line per run to results/e1.jsonl.

Figures and tables. (1) Perplexity vs bits per weight for both models (one marker per format). (2) SQNR per format. (3) Table with all numbers.

How to compare with the literature. Egiazarian et al. and Four Over Six report W4A4 (weights and activations) and word perplexity, so the numbers will not match ours. Compare trends (ranking of formats, size of gaps), not values, and say so.

E4. MXFP4 scale selection at equal storage Ziad

Claim tested. The OCP MX algorithm rounds the scale exponent down and clamps the largest values (MX paper, Algorithm 1). NVIDIA rounds MXFP4 scales up to avoid saturation, which wastes up to a binade (NVFP4 paper, Appendix B.4). Four Over Six's trick cannot apply to MXFP4 because E8M0 only steps by factors of 2 (their §5.2). Which rule gives lower error?

VariantRule per 32-element blockBits / weight
MXFP4-floor (OCP)X = 2^(floor(log2 max) − 2); clamp to ±64.25
MXFP4-upsmallest power of two with max / X ≤ 6 (no clamping)4.25
MXFP4-besttry X and 2X; keep the one with lower block MSE4.25
Optional: NVFP4 + 4/6replicate Four Over Six: scale max to 6 and to 4, keep lower MSE4.5

Report weight MSE, SQNR, clamp fraction and perplexity on both models. This reuses the E1 code, so it is cheap once E1 works. Cite Egiazarian Appendix H (MXFP scale fitting) as related prior work, not as ours.

E2. Cost on 32-bit general-purpose hardware Moaz (described in the draft, results in the final)

Claim tested. Without native FP4 hardware, each weight must be unpacked and decoded in software, so the bandwidth saving may be cancelled by extra instructions.

Kernel. A dot product of length N with weights in each format and FP32 activations:

  • FP32: 4 bytes per weight, one fused multiply-add.
  • INT8 + per-block FP32 scale: 1.125 bytes per weight; integer to float, multiply-add, scale per block.
  • MXFP4, software decode: 0.53 bytes per weight; extract a 4-bit code (shift and mask), look it up in a 16-entry float table, multiply-add, then multiply the block sum by the block scale (from the E8M0 exponent).
  • Optional MXFP4 with a 256-entry table decoding two codes per byte.

Platforms.

  1. SparkFun Edge (Cortex-M4F, 96 MHz). Reuse the project's Docker toolchain and DWT cycle counter. Weights in Flash, activations in SRAM, N = 4096. Report cycles per weight, bytes per weight, code size.
  2. Moaz's laptop (x86-64) and Ziad's M1 (ARM): the same C file with -O3, N large enough to exceed the caches (e.g. 64 M weights) so the loop is memory-bound, and small N (fits in cache) to see the pure decode cost. Report GB/s of weights streamed and time per weight.

Expected outcome (to be checked): fewer bytes per weight but more cycles per weight for MXFP4. Whether it is faster overall depends on whether the platform was memory-bound.

E3. Analytical model: specialized vs general-purpose Moaz

For batch-1 token generation each weight is read once per token. Time per token ≈ max(weight bytes ÷ memory bandwidth, weights × decode-and-MAC time per weight). Weight bytes = parameters × bits per weight ÷ 8.

  • Specialized (Blackwell): decode is free in the Tensor Core, so the best case over FP16 is 16 ÷ 4.25 = 3.76× (MXFP4) or 16 ÷ 4.5 = 3.56× (NVFP4). Compare with reported 2.2× end-to-end (Egiazarian et al., p.10) and 4-6× math speed (NVFP4 paper, Table 1).
  • General-purpose: use E2's measured time per weight and a measured memory bandwidth for the laptop and M1 (a simple copy benchmark). For the Cortex-M4F, use the project's measured Flash and SRAM rates.
  • Output: one roofline-style figure and a table of predicted time per token for GPT-2 and Qwen3-1.7B in FP16, INT4 and MXFP4 on each platform.
